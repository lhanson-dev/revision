# First Supabase Migration Execution Plan

Status: migration artifact prepared; not yet applied to the live Revision Supabase project.

## Migration artifact

`supabase/migrations/20260817134107_first_additive_regularisation.sql`

The filename was generated by Supabase CLI v2.111.0 using `supabase migration new first_additive_regularisation` in GitHub Actions. The temporary generator workflow was removed from the branch after the file was created.

## Scope

The migration is additive and deliberately narrow:

1. create `revision_private` for internal trigger code;
2. create `public.profiles` with one row per auth user;
3. add durable `is_test_user` classification;
4. enable RLS and allow authenticated learners to read only their own profile;
5. explicitly prevent browser clients from mutating profile classification;
6. explicitly allow trusted `service_role` processes to read and update profile classification;
7. create future profile rows automatically after new auth users are created;
8. backfill profiles for existing auth users;
9. add positive `schema_version` to `public.revision_progress` with default `1`;
10. preserve the existing JSON state, primary key, foreign key, RLS policies and learner rows.

## Before application

Re-check immediately before execution:

- project is healthy;
- current auth-user count and progress-row count;
- `public.profiles` does not already exist;
- `revision_progress.schema_version` does not already exist;
- current `revision_progress` policies still match the recorded baseline;
- current Supabase security/performance advisors;
- migration file on the approved PR head has not changed.

## Application gate

Applying this migration is a high-risk production database write.

It must not be applied merely because this artifact PR is merged. A separate explicit Founder instruction to apply the approved migration is required.

## After application

Run `supabase/tests/first-additive-regularisation-verification.sql` and confirm:

- profile count equals auth-user count;
- zero auth users are missing a profile;
- current progress-row count is preserved;
- all progress rows have `schema_version = 1` initially;
- RLS is enabled on profiles;
- authenticated users have SELECT only on profiles;
- anon has no profile access;
- service role has SELECT and UPDATE only;
- signup trigger and private trigger function exist;
- existing `revision_progress` ownership policies remain present.

Then re-run Supabase security and performance advisors.

## Runtime security checks

In addition to catalog verification, use dedicated synthetic test identities to prove:

- learner A can read learner A profile;
- learner A cannot read learner B profile;
- learner A cannot insert, update or delete profile classification;
- anonymous access is denied;
- existing learner progress can still be read and saved.

Do not use normal learner accounts for destructive or cross-user security tests.

## Rollback posture

No automatic rollback should be executed after production use begins because removing the table/column could discard new information. If application fails before any dependent feature is released, rollback can be considered through a separately reviewed migration. Prefer forward repair once production code depends on the schema.
